- 把前面讲过的 MQTT 心跳机制与遗嘱机制，实际用到 ESP8266 上，实现遗嘱功能。

### 示例程序一：MQTT 遗嘱基本应用

程序最开始两个头文件大家都见过，没什么好说的。接下来这里是连接 WiFi 的信息，这里是要连接 MQTT 服务端的地址，然后建立了两个对象，一个是联网用的对象，一个是 PubSubClient 库的对象。这些都见过，就不浪费时间了。

先补充一句：这段程序其实大部分内容我们之前都写过，包括连接 WiFi 的函数、设置工作模式的语句，所以这节课的重点是遗嘱相关的部分，其他的内容我会一带而过。

接下来这里是新的内容，下面仔细看看这三条语句。它们各自建立了一个常量，一共建立了三个常量。

第一个常量，是 ESP8266 连接服务端以后，这个客户端它的遗嘱信息的具体内容，内容是什么呢？是 `Client offline`，也就是客户端离线了。换句话说，如果这个 ESP8266 客户端和服务端产生了意外断开连接，服务端将会把这一段内容分发给订阅了 ESP8266 遗嘱主题的这些客户端。这就是这条语句的作用。

接下来第二个常量，它是告诉服务端，这个遗嘱信息它的 QoS 级别为 0 级。QoS 是遗嘱的服务质量等级，这里是 0 级。

接下来是 WillRetain。Retain 是什么？大家记得吗？保留。那么这里就是设置遗嘱信息的保留标志为 `False`。

这三个常量将会在程序的后面用到。具体来说，你记住这三个常量它们各自的作用就可以了。

接着来到程序的 setup 函数。启动串口通讯，设置工作模式，连接 WiFi，然后这里设置服务端相关的信息，这是服务端的地址，这是服务端的端口号。

接下来这条语句非常重要。这条语句利用 PubSubClient 库中叫做 `setKeepAlive` 的这个函数。这个函数从英文名字就能猜到它的作用了：它就是设置心跳间隔时间的，也就是客户端在连接服务端的时候，它会告诉服务端我的心跳间隔时间是多少——这里是 10，代表 10 秒钟。这就是这条语句的作用，这是我们第一次见到它。

接下来我们重点看这里，这段程序将会实现 ESP8266 客户端来连接 MQTT 服务端。连接服务端的时候是有一些特殊操作的，为什么呢？因为如果还记得的话，我们之前给大家讲过，当客户端在连接服务端的时候，它会在客户端报文中把遗嘱的相关信息告诉服务端，也就是这里红框这一系列的内容，这是上次给大家讲过的。我们回到程序来看连接服务端的这个函数，来看看这个函数的具体内容。

这里要特别强调的是：遗嘱的相关信息并不是单独发送的，而是包含在客户端连接服务端的这个连接报文中的。也就是说，客户端只有在连接服务端的这一刻，才有机会把遗嘱的相关信息告诉服务端。如果连接的过程中没有把遗嘱信息带过去，那么后面就没有机会再补充了。这也是为什么遗嘱的所有参数都集中写在 `connect` 函数里的原因。

首先函数刚开始，这里没什么要说的，就是建立我们这个客户端的 Client ID。然后我们建立一个字符串类型的变量，这个字符串变量的名字叫做 `willString`。刚才我说过 will 可以作为遗嘱的意思，`willString` 就是遗嘱的字符串。那么这个遗嘱字符串的内容是什么呢？它是 `-Maker-`，后面跟的是客户端的 Mac 地址，然后 `-` 再跟上客户端的名字。从这里我们就建立了遗嘱主题的名称。不过这个遗嘱主题的名称现在是一个字符串形式建立的，我们后面的程序中将要用到这个名称。

接下来用到 `connect` 这个函数，不过 `connect` 函数它能接受的遗嘱主题的名称，必须是一个字符数组，所以我们在这里做一个转换。转换以后的字符数组名叫 `willTopic`。这个 `willTopic` 在哪儿用呢？正是在 `connect` 函数中的第二个参数。

这个 `connect` 函数它的参数比较多，我们来把它整个打开。在这两个括号之间的所有内容都是 `connect` 函数的参数。首先第一个是什么呢？是 Client ID。第二个就是这个遗嘱主题的名字，我们刚见到它，就是 `willTopic`——我们回到代码中把它高亮，这样你看得清楚一点，第二个是遗嘱主题的名字。第三个呢？第三个是遗嘱 QoS。第四个是遗嘱保留标志。第五个是遗嘱消息内容。后面这三个，正是我们前面建立的那三个常量。

接下来我们要重点看一看这第五个参数。这个参数的内容是 `Client offline`，它是怎么作为参数放进去的呢？请看这里，这个参数实际上是一个字符串，但是我们看到它前面加了括号并且加了一个 `L`，这说明它是把这个字符串强制转换成了字符数组以后，作为参数传到 `connect` 函数中的。

到这里，`connect` 函数的参数我们全部都讲完了。也就是说，当客户端在连接服务端的时候，它把遗嘱的内容、遗嘱的 QoS、遗嘱的保留标志、遗嘱的主题都一同告诉了服务端。这就是遗嘱机制工作的第一步。

程序后面的内容就是连接服务端成功以后，串口会输出一系列内容告诉我们它现在连接的服务端地址是什么、它的客户端 ID 是什么，以及遗嘱主题是什么；如果没有成功连接的话，那就通过这一系列程序设计告诉我们连接失败了。

### 示例程序二：实现设备在线状态发布

下面来看第二个示例程序。这个示例程序可以利用 MQTT 的遗嘱机制实现这样一个功能：只要我们订阅了这个设备的 MQTT 遗嘱主题，我们就可以实时地掌握当前这个设备是不是在线。

接下来还是把这个示例程序复制并粘贴到 Arduino IDE 中，看它具体的工作状态。程序粘贴好了，首先我们来看看它的工作状态。我已经把程序上传了，接下来打开串口监视器，然后按下开发板上的复位键。随着按下复位键，可以看到开发板刚开始告诉我们正在连接 WiFi，然后它告诉我们已经连上了 MQTT 服务端，接着它告诉我它的 Client ID 是什么，以及它的遗嘱主题是什么——这里就是它的遗嘱主题了。

这些都跟刚才的程序很像，不过这里比刚才的程序多了一行内容。这行内容是什么呢？就是它会通过这个遗嘱主题向外发布当前设备的在线状态。我们知道，现在它已经连接好服务端了，所以它当前向这个遗嘱主题发布的信息是 `Client online`。如果一旦它发生意外断线，这个时候它就会通过这个遗嘱主题向其他的客户端告知我现在已经离线了。

具体是怎么工作的呢？可能这么说不是很清楚，我们接下来演示一下。

现在这个开发板还是在线的状态。接下来我们用 MQTT.fx 这个软件，先连接服务端，然后订阅它的遗嘱主题。遗嘱主题的内容是什么呢？这里就是它的遗嘱主题，我们把它复制，然后粘贴到即将订阅的主题这里，点击 Subscribe。请看，我刚订阅这个主题，这里马上就出现了这个客户端的在线状态，是 `Client online`，告诉我们这个客户端是在线的。

好，那我们现在尝试着把这个客户端让它意外断线，看看是否能够通过遗嘱主题收到它离线的信息。接下来我要断开我的开发板。现在我把它断开，好，现在这个开发板和电脑这边断开了，也就是产生了一个意外断开的状态。我们看到收到一条新的信息 `Client offline`，就是客户端离线了。

我们现在再把这个开发板和电脑连上，让它重新连接。好，现在开发板和电脑已经连接好了，我们等一等，请看，当我把开发板和电脑连接好以后，我马上收到一条新的状态 `Client online`。我再断开，过一会儿我们又会收到一条新的消息，只要这个客户端意外断开，它就会收到新的消息，请看，又收到一条新的消息 `Client offline`。

通过这个客户端的遗嘱主题，我们就可以实时地掌握这个客户端它的在线还是离线状态。那这是怎么实现的呢？

这段示例程序实际上是在刚才我们讲过的示例程序一的基础上添加了一些内容，所以在接下来的讲解中，我还是着重讲重点的部分，其他地方就很快地带过去。

程序刚开始这两个头文件不用说了，接下来是 WiFi 连接信息、MQTT 服务端的地址、两个对象。接下来这些语句是客户端连接服务端的时候它的遗嘱设置，其中第一个就是遗嘱消息的具体内容 `Client offline`，这和上一个示例程序是一样的。这里也和上一个示例程序一样，遗嘱的 QoS 也是 0 级。但是这里注意，这是遗嘱保留标志，这个保留标志我们在上程序中是 `false`，而这个程序中把它设置为 `true`。

换句话说，我们这段示例程序是让 ESP8266 开发板在连接服务端的时候，它所设置的遗嘱是以保留的形式来发布的。注意，遗嘱保留为 `true`，这是不一样的地方。这些内容后面我们会实际用到。

接下来这里是 setup 函数，然后启动串口通讯、设置工作模式、连接 WiFi、设置服务端地址，以及设置心跳间隔时间，这里还是使用 10 秒钟。实际上我在这里使用 10 秒钟是为了给你做演示，在实际使用中我们没有必要把这个时间设置得这么短，比如默认的一分钟是足够了。通常如果我们把这个心跳时间间隔设置得过短的话，会浪费不必要的网络资源。

接下来这里重点讲的是连接服务端成功以后这一部分。这里我们先建立的是具体要发布的上线信息，这是一个字符串，内容就是 `Client online`。那么这个字符串同样的我们要把它进行一个转换，转换成什么呢？转换成一个字符数组。原因也跟大家讲过多次了，原因是我们在发布消息的时候，`publish` 函数它的参数必须要使用一个字符数组。

在讲这个函数之前，先说一下遗嘱主题的名称。这段程序里的遗嘱主题名称，和上一个示例程序中我给大家讲的是一样的，遗嘱主题名字是什么？就是 `-Maker-`，后面是开发板的 Mac 地址，最后加上它自己的名字，建立好遗嘱主题名称以后，接着开发板就要尝试连接服务端了。

这里通过 `connect` 函数给它一系列的参数，请看这一系列参数，我们利用这一系列参数，客户端就可以把它的遗嘱的相关内容以及设置告诉服务端了。如果开发板成功地连接到服务端上，那么这个 `connect` 函数将返回为真，也就是说开发板将会通过串口输出一些信息，告诉我们它连接的服务端地址、它的客户端 ID 是什么，以及它的遗嘱主题名称是什么。这些都跟刚才程序是一样的。

不过后面这里注意，这里是一个新的内容。当开发板把串口监视器这些信息输出完以后，紧跟着它就会执行一个函数，这个函数的作用是：开发板只要一成功连接服务端，它马上就会向它的遗嘱主题发布一个当前开发板在线的状态。具体是怎么实现的呢？我们来看看这个函数。

这个函数叫做 `publishOnlineStatus`，就是发布在线状态的意思。我们来看它的具体内容。这个函数刚开始同样的也是建立遗嘱主题的名字，当然遗嘱主题名字和刚才我们那个函数中的主题名字是一样的，还是 `-Maker-` 后面加上开发板的 Mac 地址，再跟上它自己的名字，这是它的遗嘱主题名字。建立好遗嘱主题名称以后，接下来请看后面这里，建立设备在线的消息的具体内容，这个消息将以保留的形式向遗嘱主题来进行发布。

你看我们刚才给大家演示的过程中大家看到了，只要我们的客户端一上线，它马上就会向服务端通知我现在已经上线了。服务端收到信息以后，我们只要一订阅它的遗嘱主题，就可以收到它上线的信息内容了。那么这个信息内容是在这里定义的。

讲到这你有点糊涂没有关系，我们最后会给你做一个整体的讲解。你现在知道这里我们先建立的是具体发布的上线信息，是在这里建立的，这是一个字符串。

那接下来看这里的内容，这里是让客户端向服务端发布信息，发布什么信息呢？发布的信息内容正是客户端上线的这个信息，也就是 `Client online`。那么这个 `publish` 函数，首先它向谁来发布这个信息呢？它是向客户端的遗嘱主题来发布信息。而且它在发布的时候，注意一下，请看第三个参数，这是什么呢？把它设为 `true`。大家还有印象吗？是以保留的形式来发布这个信息。

为什么要以保留的形式来发布这个信息呢？请大家仔细思考一下这个问题，很重要。原因是，我们在程序刚开始的地方，把遗嘱的信息发布作为保留的形式来发布，那么遗嘱的信息的内容是它离线的时候，也就是断线时的那一条信息内容。那既然它是一个保留消息，我们要修改保留消息的话该怎么做呢？自然是要向这个主题再发布一条信息。再发布这条信息的时候，我们要修改它，那自然是要把这个保留标志设置为 `true`，这样才能修改保留消息。

以上内容我们在之前的课程中，在 2-3 讲的保留消息这里给大家讲解过，另外在 2-4 我们实际给它操作过。如果您听了有点吃力的话，说明您对这部分知识还没有掌握，我建议您如果听不懂刚才说的内容，可能是对这部分知识淡忘了，还是需要加强这部分内容，我们还会再重新讲。

刚才我说到，发布的这个信息内容是一个保留信息，那么这个信息具体内容是 `Client online`。如果成功发送的话，那么客户端就会通过串口告诉我它已经成功地发布信息了；如果失败的话呢，会通过串口告诉我们发布失败了。

到这里我们再回头来给大家整体捋一下，因为这个程序需要从整体来看才能看得更清楚。

刚才我给大家讲过，启动了这个客户端以后，它马上就会尝试连接服务端——只要给客户端通电，它第一件事情就是连接服务端。如果服务端连接成功以后，接着它就会马上向服务端发布它的在线状态。发布在线状态的时候，它是向它的遗嘱主题发布一个保留消息，也就是修改遗嘱主题中的保留消息内容，具体修改的内容正是 `Client online` 这种内容。

这样的话，任何客户端只要一订阅遗嘱主题，只要这个客户端是在线的话，马上就可以收到 `Client online`，也就是在线的保留消息。那自然了，如果我们这个客户端它离线了，就发布一个离线的消息了，离线的消息同样也是一个保留消息。假设我们这个客户端现在刚刚订阅主题，那马上它一订阅这个主题，它就会收到离线的消息了。
