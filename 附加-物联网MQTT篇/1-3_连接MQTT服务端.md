# 1-3 连接 MQTT 服务端

## 本节要点

- 掌握客户端连接服务端的两步流程：客户端发送 CONNECT 连接请求，服务端回复 CONNACK 连接确认
- 认识 CONNECT 数据包（报文）中的各项数据：Client ID、Clean Session、Keep Alive 以及若干可选参数
- 理解 Client ID 的作用，以及同一服务端上客户端 ID 不能重复的原因
- 理解 Clean Session 的含义，明确重要客户端应设置为 false，从而让服务端保存信息
- 理解 Keep Alive 心跳机制：客户端定时发送心跳信息，让服务端得知设备是否在线
- 认识 CONNACK 数据包中的 Session Present 与 Return Code（连接返回码）

大家好。在上节课的课程里，我们一起学习了 MQTT 的基本工作原理。我曾经给大家讲过，对于 MQTT 的客户端来说，无论 MQTT 客户端是发送消息还是接收消息，实际上它们都是跟这个 MQTT 服务端进行通讯的，客户端之间不会自己单独进行通讯。那么要想和 MQTT 服务端进行通讯，首先要做的第一件事情是什么呢？首先它们要通过物联网和服务端连接上，当它们连接上服务端以后，然后才能够实现向服务端发送消息或者接收消息。那么在这一课里，我们一起来学习 MQTT 客户端是如何和服务端来实现连接的。

MQTT 客户端连接服务端可以分成两步。第一步，请看，是 MQTT 客户端向服务端发送连接请求；这第一步。第二步，是 MQTT 服务端接收到了客户端请求以后，它将会回复给客户端一个连接的确认。这听起来感觉挺简单的，事实上这个听起来简单，但实际做起来也并不是那么简单。为什么这么说呢？

首先我想问你一个问题，我刚才说了客户端想连服务端，首先它要向服务端发送请求。怎么它就发送请求了呢？好像我给自己讲一讲。客户端要向服务端发送请求的话，它是通过物联网向服务端首先发送一个数据包，注意，它现在只是向服务端发送一个请求连接的数据包，实际上它还没有和服务端连接上。那么这个数据包的名字叫做 CONNECT，这个叫做 CONNECT 的数据包。数据包感觉挺好理解的，可以把它理解成一包数据。那么具体这个 CONNECT 数据包里面的内容是什么呢？我们后面会给你做详细的介绍。

现在请注意一点，就是客户端向服务端发送连接请求的时候，客户端是通过物联网向服务端发送一个叫做 CONNECT 的数据包。同理，当服务端接收到客户端发来的这个 CONNECT 数据包以后，它会回复一个数据包给客户端，这个回复数据包叫做 CONNACK。这也是一包数据。那么这个 CONNECT 数据包里面具体有什么内容呢？我后面会给你做详细的介绍。到这里我们就给您初步地介绍了这个客户端想连接服务端它的基本流程。

那接下来我们就来具体看一看这个数据包里面到底都有什么。我们来看这个 CONNECT 数据包它里面所包含的内容。请看这个示意图，这是为了向您阐述这个 CONNECT 数据包里面到底有什么内容。左边这一栏，请看，这里标的是名称，右边这一栏标的是内容，这什么意思呢？我跟大家说过，这个数据包里面有很多个数据，而每一个数据都有自己的名称，而每个数据也都有自己的值。这个就特别特别像我们在编程的时候一个一个的变量，我们知道每个变量都有自己的名称，而且这个变量也都有自己的值。同样的，在我们这个数据包里面也是，它有一个一个的变量，每个变量所对应的值。另外，这个数据还有自己这个数据类型。

请看我们第一个，Client ID，就是这个叫做 Client ID 的这个数据名称，它所对应的这里这个值，请看这是一个字符串类型的这么一个值。请注意，我们这右侧所写的这都是一个个的示例内容，并不是说我们每个数据包里面所包含的这些数据它对应的值只能是这几种，并不是，这只是给你举一个例子。我们看 Client ID 我们再给你举个例子，它这个值可能是叫做 Client-1，这是一个字符串型的值，它可能也是 Client2、CSN，都有可能。

同样的你看这个 Clean Session，这个叫做 Clean Session 这个数据，它所对应的值呢 true，这应该是布尔型的这么一个数据，同样的它也可能是 false，这数据可能 true 可能是 false。同样的后面都是这样的一个原理。这里有一个整型的，你看 Keep Alive 这个对应的值呢是 60。

另外可能细心的朋友已经发现了，对于这个 CONNECT 数据包里面它所对应这些数据，有些数据后面有一个括号写了一个"可选"这两个字，这什么意思呢？这样就是说在 CONNECT 数据包里面有些数据是可有可无的，写着可选的这些数据都是可有可无的数据，没有写可选的这些数据就是必须要有的。简而言之，对于一个 CONNECT 数据包里面，它肯定是有你看肯定有一个叫做 Client ID 的这么一个数据，它这个值具体什么内容，这个是根据不同的数据内容可以自己来改。好，我还说回来，CONNECT 数据包里面它肯定是有一个叫 Client ID 的数据，还有那个叫 Clean Session 的数据，肯定有一个叫做 Keep Alive 的，这三个是必须要有的。那么至于它有没有比如说叫做 Username 或者 Password 这些数据呢，这是不一定有的，有有的没有。

另外讲到这里我要强调一点，在这个 MQTT 的很多文档中，经常会把一个 CONNECT 这样的这种数据包叫做"报文"，报是报纸的报，文是文章的文。这个报文实际上就是一个数据包。我在这里为了便于您理解，我在后续课程中就管它叫数据包了，我就不说什么报文了，不过你要知道，当您在和人沟通的时候有人提到说这是个 CONNECT 报文，你知道是什么东西。

好，那讲到这里，我不知道有朋友会不会感到好奇，这个数据包里边有这么多个数据，这些数据都干什么用的呢？请您务必注意，这些数据每一个都非常重要，包括这些写着可选的这些数据都非常非常重要，不用说这个可选了、就是可学可不学了，都很重要。事实上，这一个一个的数据是客户端在向服务端连接的时候，它告诉服务端我后面跟你进行通讯的时候是如何来进行通讯，也就设置这个通讯的模式。如何来设置呢？是通过这个 CONNECT 这个数据包里面的数据来进行设置的。所以说这个 CONNECT 数据包以及这里一个个数据都非常非常重要。实际上这 CONNECT 数据包里面这些数据它们所涉及的知识内容将会贯穿整个 MQTT 协议这个教程的全部内容。

我们在这节课里面先从比较基础的一些数据入手。哪些比较基础的数据呢？而这些没有标写这个可选内容的，也就是必选的这几个数据，第一个 Client ID 是什么，第二个 Clean Session 是什么，第三个 Keep Alive，这三个数据。其他几个可选内容我们在后续的课程中会给大家做详细的讲解。虽然这节课的内容偏理论，但是这些数据您一定要先记清楚名称和作用，因为后面无论使用电脑上的 MQTT 客户端软件，还是使用 ESP8266 开发板编写程序，都要反复地填写或设置这几个参数，提前理解了它们的含义，操作时就不会盲目。好，那下面我们来开始讲解我们第一个数据 Client ID。

Client ID 它的作用是什么？这个 Client ID 它的作用就相当于这个客户端的名字。那么客户端在尝试连接服务端的时候，它首先要告诉服务端我的名字是什么，这样在后续的通讯中，客户端才能够使用这个名称来对这个客户端进行识别。如果客户端连接时不提供名字，服务端就没办法区分谁是谁，也就没有办法针对某一个客户端做单独的设置和记录了。值得注意的是，对于同一个服务端来说，不同的客户端它们的这个 Client ID 是不能相同的。请注意我在这里强调的是，对于同一个服务端来说，这个服务端上面所连接的所有客户端是不能够有相同的 ID 的。因为我们这个服务端是通过这个 ID 来对客户端进行管理的，如果有两个客户端有相同的 Client ID 的话，那这个就会造成混乱。所以在同一个服务端上不能有两个客户端拥有相同的 Client ID，这个点非常重要，请大家注意。如果您自己给客户端起名字的时候拿不准，那么建议使用一串不会重复的字符来作为客户端的 ID。

好了，那么关于这个 Client ID 我要给你介绍的内容就是这些了，我们继续往下看。看下面这个数据叫做 Clean Session。这是两个词，Clean 是干净，Session 这在网络术语中是会话的意思，干净会话。这什么意思啊？是说我们这客户端要讲文明礼貌、不能说脏话，所以要干净会话吗？当然不是，开玩笑。那么这个 Clean Session 还要给你讲一讲，话就得好好的说一说。

这个 MQTT 通讯所应用于物联网的这些特点，我们知道物联网这个网络连接并不是总是很稳定的，而且很有可能这个网络通讯的带宽也不是特别的理想。比如在之前给大家介绍过，MQTT 这个协议最早是设计给卫星通讯的，那卫星通讯这个带宽肯定是非常非常宝贵的。因此我们要对不同的 MQTT 客户端，根据它对系统运行的重要性，我们要对它进行一个区别对待。可能我这么说大家有点糊涂，这很简单，我给大家举个例子。

比如说有一辆自动驾驶汽车，这个自动驾驶汽车有很多部分组成，其中包括有自动导航系统，比如说它有车载的娱乐系统等等。我们就说这个自动导航系统，它这个自动导航系统现在正在通过 MQTT 协议在和一个云端自动驾驶平台进行实时通讯，也就是说这个自动驾驶汽车它的前进、左转、右转所有的这些动作都是通过云端的一个自动驾驶平台进行控制的。那这个云端的自动驾驶平台通过 MQTT 协议向这辆自动驾驶汽车所发送的控制指令，对这个汽车来说是非常非常重要的，如果这个指令没有得到及时的准确的送达的话，会导致这个汽车它的驾驶出现安全事故，这是很严重的一个问题。

那同样对这辆自动驾驶汽车它这个车载娱乐系统，如果没有及时地收到云端的控制平台发过来的一些控制信息，比如说换一首歌、调整一下音频的音量，这些对于这个自动驾驶汽车来说影响不是很严重。由于这个原因，我们在设计这个自动驾驶汽车的时候，我们就可以把自动导航系统和车载娱乐系统把它设计成两个 MQTT 的客户端。自动导航系统它的重要性比较强，它的这个 MQTT 客户端要保证数据信息准确无误的传输；那对于这个车载娱乐系统来说，是另外一个 MQTT 客户端，它这个信息可能偶尔丢失一个两个的数据，问题不大。这个也就是我想跟您说的，对于 MQTT 协议传输来说，对于不同的客户端它们的重要性会有所区别，我们对这些不同重要性的 MQTT 客户端会进行一个区别的对待。

好，那我们还回到这个 Clean Session 的讲解中来。对于 MQTT 服务端来说，它每次向比较重要的 MQTT 客户端发送完信息以后，它会要求重要的 MQTT 客户端给它返回一个确认信息，确认这个信息是不是收到。好，如果服务端收到了这个确认信息以后，那知道这个信息客户端你收到了，没有问题。但是如果这服务端发现发送了这个信息后半天都收不到这个客户端回来的确认信息，那它可能就会着急了，唉，这个信息是不是丢了？好，如果发现客户端没有给它发送一个收到信息的确认的话，这个时候我们会怎么做呢？它会把要发给客户端这个信息先保存下来，然后它会反复地向这个客户端再去尝试发送，反复地发送，最终确保这个客户端收到比较重要的信息。

那么这个 Clean Session 它的作用正是客户端在连接服务端的时候告诉服务端，我是不是一个比较重要的客户端。那服务端也正是通过这个 Clean Session 这个数据里面所设置的信息内容，请看 true 或者 false，就是"是"或者"不是"，根据这里这个信息来判定这个客户端它是不是一个很重要的客户端。那在跟这个客户端在将来通讯过程中，我是不是需要它给我发送的信息收到确认，以确保我给发的信息这个客户端是能够准确无误地收到的。如果服务端没有及时收到客户端的确认，那服务端就会把这个可能是客户端没有收到的数据把它保存在本地。保存在本地的目的是什么呢？目的是接下来它将不断地把这个信息向客户端发送，确保这个信息能够客户端收到。这个就是 Clean Session 的作用。

说到这里我想问大家个问题，请大家想一想，如果我们这个客户端它是一个很重要的客户端，比如说它是我们这个自动驾驶汽车里边这个导航系统的客户端，好，那么这种比较重要的客户端它在连接服务端的时候，它这个 Clean Session 这里是设置为 true 还是设置为 false 呢？比较重要的客户端是在这里设置成 true 还是 false 呢？可能很多朋友会觉得是 true 了，因为"是真的"吗，那是重要的，可不是真的吗？不是，请注意，如果你说这里是 true 的话，那这是一个错误。对于比较重要的客户端来说，这里要设置为 false，也就是假的。

为什么呢？我们从这个英文字面来翻译，Clean 是干净的，Session 是会话，干净会话。什么是干净会话？就是让服务端不要保存任何内容，干干净净的，那这种情况下它才叫干净会话。那么如果干净会话是真的，那么服务端是不会保存任何信息的。那什么时候客户端才不保存任何信息呢？适合那些不重要的客户端进行通讯的时候，服务端才不会保存给这个客户端的信息。对一些重要的来说，这个地方是要保存的，保存信息就不是干净的会话了。所以如果我们要是重要的客户端，那么这个地方设置什么呢？实际上 false，不要干净会话，我们要保存的内容。这个知识点有点绕，不过请你务必把这地方搞明白，在什么情况下 Clean Session 应该设置成 true，什么时候设置为 false。好，如果刚才我跟你讲这个内容您听不太懂的话，我请您反复地把这地方搞清楚、听明白，否则的话后面我们再给您讲解 MQTT 协议的时候，你可能就会越听越糊涂了。

另外还有一个点我想在这提一下，虽然这不是我们这节课的重点，不在这儿，我想给大家提一下。好，要想让服务端对那些比较重要的客户端信息进行保存，光对这个 Clean Session 这里进行这个 false 这么一个设置是不够的，我们要在这个通讯过程中让这个通讯的服务质量是大于零的。关于这个服务质量的内容我们后边会给你讲。那到这里你就要记住，光用这个 Clean Session 设置是不够的，还有别的操作，这样我们这个服务端才能够把客户端的信息进行保存。

好了，关于 Clean Session 我要跟你讲的就是这些了，我们继续往下看。我们看我们这节课关于这个 CONNECT 数据包里面最后一个要讲的这个数据叫 Keep Alive。好，这 Keep Alive 它的中文翻译叫做心跳时间间隔。哎，一提起这个心跳，可能很多朋友首先会想到的是什么呢？和生命有关系。是这样的，我们在之前的课程中曾给大家讲解这个 MQTT 最初设计的时候，我们要照顾到这个设计协议的有几个特点，那么其中一个特点就是设备连接状态可知。这个设备连接状态可知是什么意思呢？就是服务端对于每一个客户端它这个连接的状态是可以知道的。那么这个服务端是怎么能够知道每一个客户端的连接状态的呢？正是通过一种叫做心跳机制。好，那么到这儿我就给大家讲一讲这个心跳机制是什么。服务端要想判断一个客户端是不是跟它连接上了，唯一能够判断的方法就是看这个客户端能不能给它发来信息。假如这个客户端能够给这个服务端发来信息，那没问题，这个客户端肯定是能跟这个服务端保持连接的。但是有些客户端它并不是经常地给服务端发信息，甚至有些客户端它从来不向服务端发送信息，它只是从服务端获取信息，它从来不向服务端发送信息，那这样的客户端我们怎么来判断它们是不是跟服务端保持连接的呢？这个就用到了心跳机制了。这个心跳机制是要求每一个客户端定时地要给服务端发送一个心跳信息，心跳信息的作用就是告诉服务端，我还跟你连着。

好，那么发送这个心跳信息它有个时间间隔，这个时间间隔正是这里这个 Keep Alive，也就是心跳时间间隔。我们看到，在这个视频中我们这个 Keep Alive 它这个心跳时间间隔是 60，60 是什么意思？60 秒。换句话说，当我们这个客户端向服务端连接的时候，它就会告诉服务端，我每 60 秒会定时发一个信息给你，如果你发现超过 60 秒了，你没有收到我的信息，那你就要开始紧张了，是不是我已经掉线了。这就是客户端它这个心跳时间间隔的作用。

好，那么关于这个心跳时间间隔，我们先给您讲解这些内容，后面的我们还会碰到它，那到时候我还会给您介绍更多的心跳机制方面的信息。那这里我们这个 CONNECT 数据包里面几个必选的数据内容的作用就给你讲完了，分别是 Client ID、Clean Session 以及 Keep Alive。这个也就是当客户端向服务端连接的时候，向服务端发送的连接请求 CONNECT 数据包里面几个数据的作用。您可以这样理解这三个数据的分工：Client ID 解决的是"我是谁"的问题，Clean Session 解决的是"我重不重要、要不要替我保存信息"的问题，Keep Alive 解决的是"我怎么证明自己还在线"的问题。
