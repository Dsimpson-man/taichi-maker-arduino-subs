## 本节要点

- 认识 MQTT 客户端之间通过"发布"和"订阅"两个动作来完成信息通讯：发布是客户端向服务端发布信息，订阅是客户端从服务端收取信息
- 逐项拆解 PUBLISH 报文的组成：主题名（Topic Name）、载荷（Payload）、保留标志（Retain Flag）、报文标识符（Packet ID）、服务质量（QoS）、重发标志（DUP Flag）
- 理解保留标志（Retain Flag）的作用：解决订阅者要等很久才能收到消息的问题，服务端会把消息保存在本地，客户端一订阅就立刻推送

- 使用 MQTT.fx 实际完成订阅、取消订阅、发布消息、切换 QoS 等级以及设置保留标志的操作

## 正文

大家好，欢迎来到"零基础入门学用物联网"教程 MQTT 篇。这节课给大家讲解 MQTT 客户端是如何来发布、订阅和取消订阅信息的。这几个概念其实我们在之前的课程中都给大家讲过：MQTT 客户端之间想要实现信息的通讯，是通过发布和订阅这么几个动作来实现的。那么发布是什么呢？发布是客户端向服务端发布信息；那么订阅呢？就是客户端如果想从服务端收取信息，就订阅一个信息。这节课我们就来给大家具体讲一讲，我们的客户端是如何来发布和订阅信息的。

我们打开这节课的讲义内容，也就是 1-5 发布订阅和取消订阅。在这节课里，我们将主要给大家介绍以下几个重要的概念：首先是发布消息，接下来是订阅主题，然后是订阅确认，以及取消订阅。这几个概念其实从字面上很容易理解。发布信息 publish，这个没什么好说的，就是客户端向服务端发布信息。订阅主题 subscribe，这也没什么好说的，这就是客户端向服务端订阅主题。后面这个订阅确认是什么意思呢？就是说当我们的客户端向服务端订阅了某个主题以后，这时候服务端会给这个客户端回复一个确认，这就是订阅确认。接下来请看取消订阅，这个也很好理解：客户端向服务端订阅了某个主题以后，他不想再订阅这个主题了，就取消订阅。

不过这几个概念说起来容易，事实上它们内部所涉及的一些知识，还是需要我们好好地认真学一学的。下面我们逐个给大家讲一讲。

### 发布消息：PUBLISH 报文的组成

首先我们来看看发布消息，也就是我们的客户端是如何来向服务端发布消息的。这个客户端想要向服务端发布消息的话，它同样是通过一种叫做报文的形式，也就是客户端将会向服务端发送一个叫做 PUBLISH 的报文。大家还记得吗？我们上节课给大家讲解如何用客户端来连接服务端的时候，我给大家讲过：在客户端想连接服务端的时候，它将会向服务端发送一个叫做 CONNECT 的数据包，这个数据包就是一个报文。同样的，回到我们这节课的内容中来，如果我们的客户端想要向服务端发布消息的话，它也是要向服务端发送一个数据包，换句话说也就是一个报文。这个报文有一个名字，它叫 PUBLISH。

那么这个 PUBLISH 数据包，它的具体内容是什么样子呢？请看示意图中，我们把这个 PUBLISH 数据包里面的一个一个的数据给它罗列出来了。下面我们来仔细看看这个 PUBLISH 数据包中的一个个数据的功能是什么。

首先我们从数据包中最重要的这个数据——主题名（Topic Name）——先给大家讲起。topic 是英文"主题"的意思，name 就是"名字"，说白了这个数据就是主题名字。这个数据的功能是什么？我估计一说这个翻译你也就明白了，那就是我们的这个客户端，他想要向服务端发布消息的时候，是向哪一个主题来发布。比如说我们这个客户端向服务端、向主题叫做"汽车速度"的这么一个主题发布消息，那么在 PUBLISH 这个数据包中，它的 Topic Name 这个数据中就应该写上"汽车速度"这样的内容。不过我们这里给大家举的例子不是汽车速度，这里我们写的是 topic/1。这个没有关系，只是给大家举个例子。换句话说，Topic Name 这个数据就是告诉服务端，我们现在发布的这个信息是向哪个主题来发布的。

光知道向哪个主题发布还不够，我们还要知道向这个主题发布的具体信息内容是什么。比如说我们在前面的视频中，将要向"汽车速度"这个主题发布的内容是 60km 每小时。那么在我们这里，我们要向叫做 topic/1 这个主题发布的内容是什么呢？请看 Payload 后面，这里的信息内容叫做 temperature:32.5，就是温度 32.5 的意思。那么 Payload 这个数据的作用也就不言自明了，正是告诉我们这个服务端，我们现在向主题发布的具体信息内容是什么。这是 Payload。

### 保留标志 Retain Flag

我们继续往下看。这里叫做 Retain Flag，它中文名字叫"保留标志"。这个保留标志数据的功能是什么呢？我得给你好好讲一讲了。

当我们的客户端订阅了某个主题以后，他不会马上就会收到这个主题的信息，只有我们这个客户端向这个主题发布了信息以后，这个时候服务端才会把这个信息发布给订阅了这个主题的这些客户端。但这个流程有个缺点，什么缺点呢？请看，在我们这个示例中，比如说我们这个汽车，它每隔一分钟就会把当前的运行速度发布到 MQTT 服务端，这时候我们这个客户端只要一订阅"汽车速度"这个主题，他最多也就等一分钟，就能收到最新的汽车速度信息内容了。

但是在有些场景下，可能我们这个客户端向这个主题发布信息的间断时间会很久，也许可能一个小时、两个小时，甚至一天两天，他都不会发布一个信息。但在这种情况下，如果我们客户端订阅了某一个主题，他可能要等好久才能够收到这个主题的信息内容。这个其实不利于我们这个客户端的工作，因为毕竟他订阅主题，他是想获得这个主题的数据内容，那可能要等一天两天才能获得最新的数据内容，那这一天两天他就什么也干不了。

那么为了解决这个问题，我们就设计了这个叫做 Retain Flag 的机制。当客户端向服务端发送 PUBLISH 报文时，如果 Retain Flag 这个数据我们把它设置为 true，也就是真的这么一个情况下，在这种情况下，我们的客户端一旦订阅了某一个主题，他马上就会收到这个 Retain 数据包中的信息内容。换句话说，当我们的服务端收到了客户端发过来的 PUBLISH 数据包的时候，他如果看到 Retain Flag 这个地方它是真的，在这种情况下他就会马上把这个数据内容保存起来。保存的目的是什么呢？保存的目的就是：无论任何时候，只要有客户端订阅了这个主题，那么服务端就马上把这个数据内容发送给客户端，而不用等到这个客户端向这个主题发布信息以后才能够发送信息。他会把设置为 true 的这些数据保存在本地，只要客户端刚一订阅这个主题，马上他就把这个主题所保存的信息内容发送给客户端。

我们再把这个过程捋一遍。在没有保留标志的情况下，服务端只是把收到的信息"顺手转发"给当时在线的订阅者，转发完就把这条信息丢掉了，他不会替你保存。所以在订阅之前发布出去的信息，订阅者是永远收不到的，只能干等着下一条。而一旦我们把 Retain Flag 设置为真，服务端就多做了一个动作，就是除了转发以外，还要把这条信息作为这个主题的"当前值"保存下来。以后不管什么时候，只要有新的客户端订阅了这个主题，服务端就立刻把保存下来的这条信息推送给他，让他一订阅就能马上拿到当前的状态，不必再去等待下一条信息的到来。举个例子，假如有一个温度传感器，它每一小时才发布一次当前的温度，那么订阅者如果刚订阅上这个主题，就可能要枯等一个小时。但如果传感器发布温度的时候把 Retain Flag 设置为真，那么新订阅的客户端一订阅就能立刻收到上一次发布的温度，马上就知道现在大概是多少度，这对很多应用来说是非常有用的。

关于 Retain Flag 的功能，我先给你讲这些就够了。那么后续的课程中，我还会对这个 Retain Flag 做更深入的讲解，并且我还会对它进行一个操作的演示，到时候您看看这个操作，也许对它们就会有更好的理解了。目前我光这么讲可能还比较抽象。到这里，我们先把这个 Retain Flag 先讲到这里。

### 报文标识符 Packet ID

我们继续往下看。我们来看这个排列在第一位的，这里就叫做 Packet ID。packet 它是"包"的意思，那么在这里自然就是数据包的意思，id 实际上就是给我们这个数据包加上一个 ID。顾名思义了，这个 Packet ID 数据的作用就是为我们这个 PUBLISH 数据包打上一个编号，这个编号的作用正是用于服务端来管理数据包使用的，这就是 Packet ID 的作用。相当于我们这个数据包，我们给它起一个名字，但这里我们不能给它起名字，我们要给它做一个编号，这个 Packet ID 就是我们这个数据包的编号。

那服务端拿着这个编号干什么用呢？因为服务端同时要处理很多很多客户端发过来的数据包，这些数据包有的可能是重发的、有的可能是新的，服务端需要有一种办法把同一个数据包的不同副本认出来，才不会把同一条信息重复地送出去，或者把不同的信息搅在一起。这个 Packet ID 就是起这个作用的。要提醒您的是，Packet ID 是和 QoS 服务质量等级配合使用的，服务端在向客户端回复确认信息的时候，也会带上这个编号，这样双方就能对得上号。这一点等我们后面讲服务质量等级的时候，您就会体会得更清楚了。

### 服务质量 QoS

接下来我们再往下看。我们来看这里这个 QoS。事实上在之前的课程中，我曾经给大家提过 QoS 这个概念，它是"服务质量"的意思。关于这个服务质量的概念，我在这节课里先不给大家做深入的讲解，我先简单地讲一讲。我之前课程给大家讲过，不同的 MQTT 客户端，它们所负责的工作的重要性是不同的。有些 MQTT 客户端它所做的工作非常非常重要，那这样的客户端，我们就希望它的信息能够准确无误地发布和送达；但是有些客户端，它相对来说信息重要性就低一些，对于那些客户端来说，它的信息可能会丢失，但不会影响到整个系统的运行。

那么这个 QoS 服务质量，正是用来决定我们这个数据信息它的重要性的。服务质量级别越高，它的重要性也越高。如果服务质量为零的话，那么这个是服务质量最低级的。简而言之，QoS 这个数据中所存储的内容，正是来决定我们这个 PUBLISH 数据包它的重要性的。这里这个数字 1，说明它的服务质量级别是一。好，这个是 QoS。

### 重发标志 DUP Flag

最后我们再来看这个 DUP Flag。DUP Flag 的中文翻译是"重发标志"。重发什么呢？就是重复发送的。那为什么是重复发送的？我们之前跟大家讲过，为了确保某一条信息能够准确无误地送达客户端，它可能会重复地发送某一条信息。那么如果这个信息是重发的话，那么就是重发标志为真；如果这条信息不是重发的，自然就是重发标志为假。这个就是 DUP Flag 重发标志的作用。

讲完这个 DUP Flag 重发标志以后，我们这个 PUBLISH 报文中的基本内容就给大家介绍完毕了。可能到这里大家会有一种感觉：这个 MQTT 协议好无聊啊，全都是理论知识，没有意思。没有办法，毕竟我们在掌握一个新的技术知识之前，我们先要对这个理论知识进行一个非常深入的了解，了解了理论知识以后才能真正实践。现在就请您耐着性子，我们认真地把这些理论搞清楚弄明白，这样后面我们在实际动手操作的时候，才能更加清楚、更加明白我们这个操作的内容是什么。所以现在请您继续耐着性子，我们继续来学习后面的内容。

### 订阅主题 SUBSCRIBE

后面具体是什么内容呢？我们接下来要来学习我们的客户端是如何来订阅主题的。订阅主题的时候，客户端将向服务端发送一个叫做 SUBSCRIBE 的数据包。subscribe 是英文"订阅"的意思。发送这个 SUBSCRIBE 数据包中，它有一系列的数据内容，那么其中最主要的数据内容是订阅主题名。注意，在一个 SUBSCRIBE 数据包中，它可能会包含有多个订阅主题名，也就是说一次性的它可以订阅一个主题，也可以一次性订阅多个主题，这就是 SUBSCRIBE 数据包的主要作用。

那么这个 SUBSCRIBE 数据包，客户端向服务端发送以后，服务端收到它就知道："哦，这个客户端想要订阅这个主题了。"服务端就会把这个客户端登记到这个主题的订阅者名单里。以后只要有人往这个主题发布信息，服务端就会把信息推送给名单里的所有人。请注意这里的关键点：发布者和订阅者之间彼此是完全不知道对方存在的，他们谁也不认识谁，所有的事情都是通过服务端来中转的。这也是 MQTT 这种发布订阅模式的一个很大的好处，就是发送信息的一方和接收信息的一方不需要建立一对一的连接，大家各发各的、各收各的，非常灵活，也非常省资源。这个订阅主题名说白了就是订阅哪个主题，比如我们这个实例中，这两个客户端订阅的主题名就是"汽车速度"，那么这个订阅主题名就是"汽车速度"，这很直观。不过有一个概念很重要，就是在这个 SUBSCRIBE 数据包中，它也包含有一个叫做"服务质量等级"的这么一个概念，也就是说每一个 SUBSCRIBE 数据包，它同样包含有一个数据，它定义了这个 SUBSCRIBE 的服务质量等级。不过我们这节课不会给它做深入的讲解，我们后边会给大家讲解得更加清楚一些。到这里你就知道，SUBSCRIBE 数据包中同样有这个服务质量等级的数据内容。这个就是订阅主题这个数据包中的主要内容。

### 订阅确认与订阅返回码

接着往下看，我们来看这个订阅确认。订阅主题、订阅确认，这其实很好理解：当我们的客户端向服务端订阅了某个主题的时候，首先他要向服务端发送订阅主题的数据包；那么当服务端收到订阅主题数据包以后，他会回复一个数据包给客户端，那么这个回复的数据包就叫做订阅确认。这个订阅确认数据包中最重要的内容叫做"订阅返回码"。

这个订阅返回码是干什么用的呢？请大家回忆一下，当我们的客户端想要连接服务端的时候，他向服务端发送 CONNECT 数据包，那么服务端向客户端会回复一个连接确认的数据包，在这个连接确认的数据包中，它其中也有一个返回码，它叫"连接返回码"。连接返回码的作用就是告诉客户端，你有没有成功地跟我连接。那么在这里，这个订阅确认数据包中的订阅返回码，它的作用就是告诉客户端，你有没有成功地订阅到某一个主题。

那么具体这个返回码的内容请看这里：如果成功地订阅了主题的话，它会返回 0，或者 1，或者 2。可能有朋友看到这里有点糊涂，到底是哪一个是成功？怎么都是成功吗？0、1、2？事实上，具体是发送哪一个返回码作为成功的确认，需要看客户端发送的这个订阅主题的时候，他所使用的服务质量等级是什么。如果客户端发送给服务端的时候，他这个服务质量等级是 0，以 0 这个服务质量等级来订阅某一个主题，那么它的返回码就是 0；如果 QoS 是 1，那么返回 1；如果是 2，那么返回 2。所以 0、1、2 这几个返回码都代表订阅成功，只不过就是根据客户端发送的订阅主题报文中的服务质量具体是哪个等级，他就会回复哪一个返回码。如果订阅失败的话，那么就回复 128 这个数字。这个就是我们这个订阅确认数据包中订阅返回码的作用。

好了，通过订阅主题这个数据包以及订阅确认数据包，我们的客户端就可以实现某一个主题的订阅，这两个数据包都是用来订阅主题的。

### 取消订阅 UNSUBSCRIBE

接下来我们来看，如果我们的客户端想要取消某一个主题的订阅的话，它可以通过客户端向服务端发送一个叫做取消订阅的数据包。那具体取消订阅数据包中的具体内容，你可以看到在这个示意图中给你列出来了。值得一提的是，在一个取消订阅数据包中，它可能会有多个主题，请看这里 topic1、topic2，这都是主题的名称，多个主题的内容是用来让我们的客户端告诉服务端，我一次性可能会取消订阅多个主题。好，一次性可以取消订阅一个主题，也可以取消订阅多个主题。

这里还有一个细节值得提一下，就是服务端在收到取消订阅的数据包以后，同样也会给客户端回复一个确认，告诉客户端这个取消订阅是成功了还是失败了。这和订阅、连接是一样的道理，MQTT 协议中凡是需要服务端配合完成的操作，服务端都会给客户端一个反馈，让客户端心里有数。我们做物联网应用的时候，就可以根据这个反馈来判断自己的操作到底有没有生效，出了问题也方便排查。另外，取消订阅以后，这个客户端就再也收不到这个主题的信息了，服务端会把他从这个主题的订阅者名单里划掉。如果以后又想重新订阅，那再发一次 SUBSCRIBE 就可以了，随时可以退订、随时可以重新订阅，非常灵活。

好了，到这里我们就把这节课主要给大家讲解的这几个重要的报文，也是重要的数据包的内容给大家讲解完毕了。那接下来我们就来实际操作，使用我们电脑中的 MQTT.fx 软件来实现发布、订阅和取消订阅的操作。
