## 正文

大家好。在上一节课中，我们讲解了互联网协议中的网络层和链路层。这节课我们继续来看互联网协议中的传输层以及应用层。

首先我们来看传输层。传输层主要是由 TCP 和 UDP 这两种协议所构成的，那么我们分别来看看这两种协议的情况。第一个我们先来看看 TCP 协议的情况。假如我们要用一个字来概括 TCP 协议的特点的话，这个字就是「稳」。为什么用「稳」字来形容 TCP 协议呢？原因是 TCP 协议的设计初衷是为了保证所有数据都能够被接收端所接收。

当然了，这里所说的「保证所有数据都能被接收」也只是一个相对的。如果这个网络出现了一些硬件上的故障，即使是用 TCP 协议，数据也可能会丢失。我再强调一遍，主要是让大家清楚：并不是说我们使用了 TCP 协议，数据就一定会被接收端接收。我们在这里用「保证」这个词，也只是说 TCP 协议相对其他的协议，比如 UDP 协议来说，TCP 协议会更稳定一些。

那么说了这么多，TCP 协议会更稳定一些，但它到底是怎么能够保证传输更稳定的呢？请看，首先，在 TCP 协议传输中，数据的传输顺序是不会被打乱的；其次，在传输数据的时候，如果这个数据有损坏的话，被损坏的数据将会被重新发送。至于这个稳定的特点，TCP 协议经常用于对数据稳定性要求比较高的这些领域，比如电子邮件或者文件传输。

试想一下，当我们发送电子邮件的时候，我们肯定希望我们所写的一封电子邮件的内容不能发生任何丢失或者改动，由于 TCP 协议有稳定的特点，所以电子邮件经常采用 TCP 协议来进行传输。另外像文件传输，我们在发送文件的时候肯定也希望文件能够完好无损地从发送端到达接收端，因此电子邮件和文件传输这两个都是比较常用 TCP 协议的。除了这两个应用场景，还有其他的一些场景，我在这里就不给大家赘述了，我们主要是了解这个 TCP 协议的特点以及它的基本应用。

说了这么多 TCP 协议的应用场景以及它的优点，那 TCP 协议有没有缺点呢？当然有了。TCP 协议正是因为它以稳取胜，所以它的传输速度相对就没有那么快。那么谁的速度比 TCP 协议快呢？这就引出了我们要接下来介绍的这个 UDP 协议。

对于 UDP 协议来说，它的特点就是「快」。当然了，我在这里所说的这个 UDP 协议比较快并不是绝对的，这里所说的快，指的就是 UDP 协议相比 TCP 协议来说传输速度要快一些。但这个 UDP 协议快是快，它是不能够保证所有数据都能被接收端所接收的，正所谓「欲速则不达」，这个数据能够很快地传输，但是这个数据并不保证能完全地被接收端所接收。

这里可能有朋友会说：那既然都不能保证数据被接收端接收，我们要这个 UDP 协议还有什么用呢？请大家留意，这里所说的「不保证」，相对来说 UDP 协议只不过是没有 TCP 协议那么稳定。比如当我们要传输数据，一旦发生损坏，那么 UDP 协议会抛弃受损的数据；另外，数据被损坏以后，采用 UDP 协议来传输的时候是不会重新发送这个受损数据的。这也是为什么 UDP 协议不能够保证所有数据都被接收端所接收。

基于这些特点，UDP 协议通常应用于对网络传输速率要求比较高、但对数据稳定性要求没有那么高的这种应用场景。比如说，UDP 协议经常用于在线语音视频这个领域，或者说 UDP 协议还经常用于网游这种领域。这一点可能很多朋友都深有体会，在网络环境不好的时候我们玩网游，经常是我们一番操作猛如虎，但是被对方打得措手不及，原因就是我们发出的操作指令数据在传输过程中被 UDP 协议所丢失了。

关于 TCP 协议和 UDP 协议这两种协议的特点，我就讲到这里，在这里不再花更多的时间了。原因是我们这个教程中对这两种协议没有特别深层次的应用，所以我们在这里主要了解一下它们的基本特点以及应用场景就够了。

不过接下来请大家留意，我要给大家讲的是我们这节课的重点了。这节课重点是什么呢？是应用层，具体来说是应用层中的 HTTP 协议，其他的这些协议在我们后面的课程中都没有涉及。那么在接下来的课程中，我将重点给大家讲一讲应用层中的 HTTP 协议。HTTP 协议可以说是最常用的互联网协议了，我们在使用浏览器浏览网页的时候正是使用这个协议。请注意，HTTP 协议并不是仅仅应用于浏览网页，它还有很多其他的用途。下面我们来看看它的详细情况。

HTTP 协议是由请求和响应构成的。HTTP 的工作模式很像是一问一答这种模式。那 HTTP 协议是怎么通过一问一答的形式来进行工作的呢？我们来举个例子。请看这幅图，左边这是我的电脑，右边请看这里，这是我们太极创客网站的这个服务器。现在我这个电脑已经连接到互联网了，我可以通过互联网来访问太极创客这个网站的服务器，也就是说可以打开太极创客的网站了。

那请您现在想一想，如果我现在要用我的电脑来浏览太极创客网站，需要经过哪些操作呢？首先我要打开浏览器，然后在浏览器的地址栏里面输入太极创客网站的网址，比如您现在屏幕上所看到的这个网址。接着我按下回车，这个回车会让浏览器将我输入的这个网址信息，具体来说是要通过我们的浏览器、使用互联网，最终发送到太极创客网站服务器。当太极创客网站服务器收到了这个请求以后，它就会想：哦，有一个用户正在向我请求网站首页这种信息。于是这个太极创客网站服务器就会自动生成一个 HTTP 响应，也就是太极创客网站首页的一个信息，最终传到了我的电脑中，于是就会在这个电脑的浏览器中显示出太极创客的网站首页了。

那么以上就是 HTTP 协议请求和响应的基本工作原理。怎么样，是不是很像是一问一答？那么在这个一问一答中，其中的「问」正是我们电脑发出的请求，「答」正是太极创客网站服务器所响应的这个网站首页信息。

接下来我们来看看 HTTP 请求和响应的详细情况。首先我们看的是 HTTP 请求。您在屏幕上看到的这一系列文字就是一个 HTTP 请求的实例了。可能有朋友看到这么多文字感觉有点紧张，没关系，我们一点一点给您分析，其实很简单。为了讲解，我们先把这个 HTTP 请求的实例分成几部分。

首先我们看第一部分，这第一部分就是这个 HTTP 请求的第一行文字，它叫做「请求行」。那么剩下的，请看，剩下的这些文字是 HTTP 请求的「请求头」部分。讲到这儿，可能有朋友会感到好奇：既然有请求头，那是不是还有别的呢？没错，对于 HTTP 请求来说，它还有一部分叫做「请求体」，这个「体」是身体的「体」。这个请求体对于大部分 HTTP 请求来说是不存在的，所以在这里我们也就把它忽略掉了。也就是说，我们现在主要关注的就是 HTTP 请求中的这个请求行以及请求头这部分内容。

那么我们先来看这个第一个，这个请求行里边的信息。首先我们看第一行中最前面这个位置，`GET`。`GET` 是一个读取请求，它意味着我们整个这个 HTTP 请求是要读取一些数据信息的这么一个请求。除了这个 `GET` 这种方法，HTTP 协议中还有其他的一些方法，不过这个 `GET` 可以说是 HTTP 协议中这些方法里面最常用的方法之一。

那么到这里您只要记住一点，就是这个 `GET` 它的作用就是要告诉服务器：我们这里有一个请求，这个请求想要读取服务器中的某些信息。具体什么信息呢？请看这个 `GET` 后面有一个斜杠，这个斜杠的作用就是要告诉网站服务器，我们这个读取请求的内容是要读取网站这个首页的信息。换句话说，就是请求网站服务器把它的首页的网页数据发过来。

到目前为止都还比较好理解，我们这个请求就是读取网站首页这么一个请求。那我们继续看，后面这个 `HTTP/1.1`，它的作用就是要告诉服务器，我们这个 HTTP 请求所采用的 HTTP 协议的版本号是 1.1 版本。这个信息的作用是为了协议版本兼容。这就好像比如我们要给我们电脑装个软件，首先第一点我们要知道这个电脑它的操作系统版本是什么，是 Windows XP、Windows 7 还是 Windows 10，对于不同的版本我们要有不同的软件版本来对它安装。同样在这里，我们要告诉服务器我们现在所使用的是什么样的版本的协议，这样的话服务器才知道怎么应对我们这个请求。

那么目前应该都还比较好理解，我们继续往下看。我们看第二句，这第二句就进入到我们整个 HTTP 请求的请求头部分了。`Host: www.taichi-maker.com`，我估计您在看到这一句以后基本上就明白了它的意思了。这个 `www.taichi-maker.com` 是太极创客网站的网址，这个 `Host` 它的意思是主机（服务器）的。那么在这里连在一起就是说，我们这个请求信息它针对的是互联网上的哪一个网址的主机，那这里自然就是太极创客网站的这台服务器主机了。

当我们把这些信息都连在一起就好理解了：这个请求就是向太极创客网站的服务器请求网站首页的信息，同时也告诉这个服务器，我现在这个请求所使用的 HTTP 协议的版本号是 1.1。

讲到这儿，不知道是不是会有朋友感到好奇：我刚才给大家讲的这个实例中，我们这个电脑是想从服务器那里获取信息，这时候用的这个请求的方法是 `GET`。但是如果我们的电脑要想向服务器发送信息，不是获取信息而是发送信息的时候，这个时候我们就要用一种新的 HTTP 请求的方法，它就是屏幕上所显示的这个 `POST`。剩下都一样，请看这里 `POST`，这里还是斜杠再往下，也就是说向这个 `www.taichi-maker.com` 这个网站的服务器，向它的首页发送信息，这时候我们用 `POST`。

讲到这儿，我就要给大家介绍一下这个 HTTP 请求中一共有多少种方法是供我们使用的。请看，在这个 HTTP 1.0 这个版本中，它定义了三种，分别是 `GET`、`POST` 和 `HEAD`，不过我们最常用的就是 `GET` 和 `POST`：`GET` 是获取信息，`POST` 是发送信息，`HEAD` 相对用得比较少一些。

可能有朋友已经注意到了，我在这里说的是 HTTP 1.0，但是实际上我刚才给大家举的这个实例中这里是 HTTP 1.1，这两个版本是不一样的。事实上这个 HTTP 协议的版本是向下兼容的，也就是在 1.1 版本中同时兼容 1.0 的内容，另外在 1.1 这个版本中还新增了其他的几种方法，这几种方法在我们后续的教程中是不会涉及到的，所以我们在这里主要强调的一个是 `GET`，也就是我们的电脑获取信息用的是 `GET`；如果我们电脑向服务器发送信息，那么就可以用 `POST`。

讲解完 HTTP 请求的第一句和第二句这两句以后，剩下的内容都是我们这个教程中不是关键的部分，所以我在这里给您做一下简单的介绍。首先我们看看这个 `User-Agent`，这是我们的电脑在向服务器发送请求的时候，告诉服务器我们这个电脑它的浏览器以及它的电脑操作系统版本这些信息。

我们继续往下看，请看这一句 `Accept: text/html`，这个是告诉服务器我们的浏览器它支持哪一种网页编程语言，这里指的就是 HTML 这种编程语言所制作的网页。接着往下看，`Accept-Language`，这是告诉服务器我们的这个浏览器它所支持的语言，也就是中文这种语言。`Accept-Encoding` 就是它所支持的压缩的信息编码的格式，比如 zip 什么的。后面的这个 `Connection: keep-alive`，就是说当服务器发送完信息以后，是不是和我们的电脑继续保持连接还是断开，`keep-alive` 就是说继续和我们电脑保持连接。

好了，关于 HTTP 协议中的请求的内容，我要给您介绍的就是这些了。我刚才说了，这个 HTTP 协议它是有请求还有响应的，一问一答，那么讲完请求以后，接下来我们来看看关于 HTTP 响应的相关内容。

您现在屏幕上所看到的就是一个 HTTP 响应的实例了，这个 HTTP 响应的第一行叫做「状态行」。为什么叫状态行呢？一会儿我再给您详细介绍。我们再往下看，接下来这两行的文字信息叫做「响应头」。我们看到响应头有这两行，这第一行比较好理解，它就是服务器在发送这段响应信息的时候的服务器时间是什么。请注意，我们在这里后面请看的是 GMT，这个服务器时间是格林威治时间，并不是我们中国的北京时间。那么第二行这个信息相对来说就复杂一些，我后面再给你讲述。关于第一行关于这个状态行以及响应头里面的这个第二行信息，我都是在后面再给你讲。

我们继续往下看，后面的请看这里是「响应体」信息。那这个响应体的内容是什么呢？请大家回忆一下，刚才我们发送一个 HTTP 请求到太极创客网站服务器的目的是什么？就是请求这个网站把它的首页信息发送到我们电脑浏览器里面去。而这里请看，这个响应体里面的信息正是太极创客网站首页的信息。当然这是一个非常简化的版本的首页信息了，不过它确确实实是一段 HTML 代码，换句话说，这个响应体里面的信息正是我们请求的信息的正文。

讲到这儿，可能有朋友会感到好奇：既然服务器已经通过响应体里面的信息直接把我们所需要的信息发过来了，那要这个状态行以及响应头它的作用是什么呢？接下来我给你仔细讲一讲这个状态行以及响应头第二行这个信息的作用。

首先我们来看第一句，这个 `HTTP/1.1` 这个信息，我们在刚刚 HTTP 请求部分中已经介绍过了，它的含义就是这个 HTTP 响应所采用的协议版本号是 1.1，关于这个信息我就不在这里赘述了。我们接着往下看，请看后面 `200`，这个代码可能有些朋友会感到有点陌生，是不是 `404` 大家会感到更熟悉一些呢？好，那么无论是 `200` 也好，还是 `404` 也好，这些都是 HTTP 响应状态码，它的作用就是以代码的形式来表达服务器在接到请求后的状态。

看这句话有点复杂，我再重新说一遍。它的作用是用代码的形式，也就是说用 `200` 也好、`404` 也好，通过这种代码的形式来表达服务器在接收到我们的请求以后所产生的状态。这个 `200` 就代表服务器已经成功地找到了 HTTP 请求的这个网页资源。注意，这里所说的是 HTTP 请求的网页资源，`200` 表示找到了。如果说了这么多您还不能理解的话，那我再给您举个例子。

比如说有一天我们到一个小卖部里面买东西，进了小卖部以后我们就跟老板说：老板，你有没有辣条？老板这时候看了看四周，非常深情地回了一句 `200`，说明什么呢？老板他找到辣条了。但是比如说我们到了小卖部里面以后，我跟老板说：老板，我要买一辆最新款的奔驰跑车，你有没有？老板这时环顾了一下四周，非常不耐烦地回了一句 `404`，那说明什么呢？说明老板这个小卖部里面是不卖最新款的跑车的。

同样的，对于我们这个服务器来说，它在返回 `200` 也好、`404` 也好，都是来告诉我们它有没有找到我们所请求的这个资源。当然了，在这个状态码后面跟的这个英文就说明这个状态码它具体含义是什么，比如 `200 OK`，这没什么好多说的，就是找到资源了；`404 Not Found`，就是没找到。

说了这么多，估计朋友们对 HTTP 响应状态码的作用已经有了一个逐步的认识了。不过说到这儿，可能有朋友会感到好奇：这个响应状态码除了 `200`、`404` 以外，是不是还有别的状态码呢？这个答案是肯定的。接下来我们来看看其他状态码的介绍。

您可以来到我们太极创客的网站，在这个「零基础入门学用物联网」这个目录页中，请看这里有一个链接是「ESP8266 互联网基础知识」这个链接，点击它进入这个页面。在这个页面里面，请看 2-5 应用层，点击它。好，在这个页面里面请注意，在这一部分有其他的这些状态码的一些基本介绍。那么关于这部分知识，如果您感兴趣的话可以到这里来看一看；如果感觉这里知识不够、不能满足您对知识的渴望的话，那么您可以通过互联网或其他资源找到这方面的相关知识。关于这个状态代码，我要给您介绍的内容就是这些了。

接下来我们来继续看。我们刚才讲完了 `HTTP/1.1 200 OK` 这一句的意思了，我们下面来看响应头中的内容。这一开始是 `Content-Type`，估计英语好的朋友可能已经看明白了，`Content` 是内容的意思，`Type` 是类型的意思，那么这两个加在一起就是「内容类型」。是什么内容类型呢？是响应体的内容类型。请看，我们这里所指的这个响应体内容类型是 `text/html`。

通过这一系列的信息就为了说明在这个响应的响应体部分，注意，我说的响应体部分，那么这个作用是什么呢？这个作用就是当我们的浏览器在接收到这些信息以后，它们就会知道在这个响应的响应体部分是 HTML 网页代码，那么浏览器也就会将这个网页代码翻译成我们人类能够读懂的这种格式，并且把这个网页的信息显示在屏幕上，以供我们查阅。关于这个响应体内容类型，我们先讲这么多，后面我再给大家做更多的介绍。

我们先往下看，请看后面这一行字，这行字 `charset=utf-8`，它呢是字符集的意思，`charset` 就是字符集，UTF-8 是一种字符集的类型。可能有的朋友见过这个 UTF-8。那么关于字符集的概念，我再给你做个简单的介绍。

相信观看我们这个教程的每一个朋友都使用过电脑，在电脑键盘上边你可以看到这个键盘上面都是英文字符，还有数字，以及那些其他的符号，叹号、井号等等这些符号。但是呢，在这么多字符中却没有中文字符，为什么呢？因为如果要是有一个键盘能够把所有中文字符都显示出来的话，那么这个键盘可能太大，不可能把它放到电脑上面使用。

那说这么多，我们现在为了解决能够通过电脑显示中文怎么办呢？这个时候就产生了一个字符集的概念。那么所谓字符集，就是通过我们现在你看这个键盘上所有这些有的这些字符，用这些字符和我们一个个的中文文字对应起来，于是电脑就知道：当它看到一系列字符以后，它就知道要写什么中文字了。

可能这么说有点抽象，我们看一个实际的例子。请看「太极创客」这四个字，我们先看「太」字，最左边这个 `&#x592A;`，那么这一系列字符就是 UTF-8 这个「太」字；另外「极」字，请看 `&#x6781;`，这个就是「极」字，等等等等。那么换句话说，当我们太极创客的网站服务器在发送网页信息到我们浏览器的时候，这时候它所发送的信息并不是一个一个的这些中文字，而是这样一种一个一个的字符。那么这些字符所采用的是哪一种字符集，就一定要告诉浏览器，那么浏览器知道这个字符集以后，它才知道怎么把这些字符和一个中文词对应起来，这个就是字符集在这里的作用。

相信您通过我刚才讲解的这行响应头的信息，已经具备一定认识了。但是讲到这儿，可能有朋友会感到好奇：我们浏览器不光是能显示文字信息，还能显示图像信息，那么当显示图像信息的时候，这时候响应是什么样子的呢？好，那你看这里，请看这里 `Content-Type` 这些还没有变化，同样和前面是一样的，但是后面这里变成了 `image/jpeg`，这个 `image` 是图像的意思，斜杠后面的就是图像的一个格式了。那么通过这个文字信息，我们浏览器就知道：哦，现在这个响应里面它是一个图像而不再是字符了。于是你的浏览器就会通过如何来显示这个 jpg 格式图像的方法，来把图像显示在我的屏幕上。

好，那么这里的信息内容也给您介绍完了。讲到这里，我请您再回忆一下，在以上实例中我们是使用互联网浏览器来讲解 HTTP 的请求和响应的，那么当我们使用 NodeMCU 开发板来开发物联网项目的时候，这时候发出 HTTP 请求的就不再是浏览器，而是 NodeMCU 开发板了；同时读取这些服务器的响应的也不再是浏览器了，也变成了这个 NodeMCU 开发板了。那么究竟如何让 NodeMCU 开发板来处理 HTTP 的请求和响应呢？这些就有赖于我们这个 NodeMCU 开发板的控制程序了。那么关于这个控制程序是如何来书写的，我们在后面的课程中会给大家做详细的介绍。

好了，到这里，关于这个互联网协议相关的内容，基本上我给大家介绍的就是这些内容了。不过最后还有一个知识点要给您介绍一下，是什么知识点呢？这个知识点很重要，请注意。

当我们在使用电脑浏览太极创客的网站服务的时候，这时候我们使用电脑输入太极创客网站的网址，可是我们输入这个网址信息，请看，屏幕上可以写出来 `www.taichi-maker.com`，这是我们的网址。有了这个网址信息以后，浏览器就知道我们人类是想要访问互联网上的一个太极创客网站服务器上的信息。于是正如我之前课程给大家说的，目的地地址就是太极创客网站的服务器了。

那这个时候问题就来了，我之前说过，我们这个太极创客网站服务器它是在互联网上有一个 IP 地址的，那个 IP 地址是什么呢？是 `11.66.88.88`。可是我们在输入网址的时候是什么？是 `www.taichi-maker.com`。诶，这个输入的是 `www` 点什么，怎么变成了到服务器这块就变成 `11.66.88.88` 了？那我们的电脑是怎么从这个 `www` 这个网址的信息转换成 IP 地址这个信息的呢？接下来讲讲这方面知识。

当我们在浏览器中输入这个网址信息以后，这个时候浏览器并不急于生成一个请求发送到这个太极创客网站服务器上去，实际上它也没办法把这个请求发到太极创客网站服务器，为什么呢？因为它根本就不知道太极创客网站服务器的 IP 地址是什么。不知道 IP 地址，它无从发这个请求，所以它要先把这个网址通过互联网发送到一个 DNS 服务器这么一个地方。那么这个 DNS 服务器在接收到了这个网址以后，会把这个网址信息通过它内部的检索系统把它转化成 IP 地址，然后 DNS 服务器会把这个地址信息发回到我们的电脑中去。我们电脑里面的浏览器收到这个 IP 地址以后，然后它才会生成这个请求，再把这个请求通过互联网发送到网站服务器上。

讲了这么多，可能有朋友会感到疑惑：何必要大费周章地先要把这个网址先发给 DNS，然后 DNS 再把 IP 地址回到我们电脑，回到电脑以后我们电脑再发这个请求到服务器上？这太麻烦了吧。这其实是很有必要的。你试想一下，如果现在我们随便说一个网站，比如说必应，`www.bing.com`，这个很好记；但是如果没有这个 DNS 服务器，我们如果想要访问某一个网站，比如这个必应网站，我们就得记住它这个网站服务器的 IP 地址，也就是四个数字，这其实是挺麻烦的一件事情。因此才会有这个 DNS 服务器的存在，让我们访问网站的时候可以更加方便、更加容易记住这些网站的地址。

## 本节要点

- 传输层主要由 TCP 和 UDP 两种协议构成
- TCP 协议的特点是「稳」，数据传输顺序不会打乱，损坏的数据会重新发送
- TCP 常用于电子邮件、文件传输等对稳定性要求高的场景
- UDP 协议的特点是「快」，但不保证数据全部送达，损坏数据会被丢弃且不重发
- UDP 常用于在线语音视频、网络游戏等对速率要求高、对稳定性要求低的场景
- 应用层中最常用的是 HTTP 协议，浏览器浏览网页使用的就是它
- HTTP 采用「一问一答」模式，由请求和响应构成
- HTTP 请求由请求行、请求头、请求体三部分组成；请求体对多数请求不存在
- 请求行中 `GET` 表示读取信息，`POST` 表示向服务器发送信息，`HEAD` 较少使用
- 请求行末尾的 `HTTP/1.1` 是协议版本号，作用是保证协议版本兼容
- `Host` 指定请求针对的主机；`User-Agent`、`Accept`、`Accept-Language`、`Accept-Encoding`、`Connection: keep-alive` 等都是请求头信息
- HTTP 响应由状态行、响应头、响应体三部分组成
- 状态码用来表达服务器接收到请求后的状态，`200` 表示成功找到资源，`404` 表示未找到
- 响应头中 `Content-Type: text/html` 说明响应体是网页代码，`image/jpeg` 说明响应体是图像
- 响应头中的 `charset=utf-8` 指定字符集，浏览器靠字符集把字符与中文对应起来
- 用 NodeMCU 开发物联网项目时，发出请求和读取响应的不再是浏览器，而是开发板的控制程序
- DNS 服务器负责把域名（如 `www.taichi-maker.com`）转换成 IP 地址，浏览器拿到 IP 后才能发出请求
